RL fine-tuning, profiled with CUPTI

vLLM rollouts + FSDP2 training on one GPU, every step traced with the CUDA Profiling Tools Interface; a study of the rollout-training mismatch of Yao, Liu, Zhang, Dong, Shang and Gao, "On the Rollout-Training Mismatch in Modern RL Systems" (NeurIPS 2025 Efficient Reasoning workshop).

What the implementation does

An instruction-tuned (SFT) model is fine-tuned with reinforcement learning on a math or puzzle dataset with rule-based rewards. As in production RL frameworks it uses two engines with the same weights: vLLM generates the rollouts and PyTorch FSDP2 computes gradients. Both run in one process on one GPU, so a single CUPTI session sees every kernel. Each training step is split into named phases:

  1. weight_sync: FSDP parameters are gathered and cast to bf16 (gather), quantized to INT8 for INT8 rollouts (quantize), and loaded into vLLM with its layer-wise reload (vllm_load).
  2. rollout: vLLM samples n responses per prompt and returns log πvllm(token) for every sampled token (processed logprobs, i.e. the true sampling distribution).
  3. reward: answers are checked (math-verify for math, exact equation check for Countdown); CPU only.
  4. advantage: group-normalized advantages (reward minus the prompt's mean, divided by its std); groups whose samples all got the same reward are dropped.
  5. old_logprob: the FSDP model re-scores every rollout without gradients: log πfsdp(θold) and the policy entropy.
  6. mismatch: πvllm vs πfsdp on the same tokens and the same weights: KL estimates, |pvllm − pfsdp|, importance-ratio extremes, and a 2-D histogram (the paper's Figure 1, left).
  7. train: PPO-clip loss over mini-batches (forward, backward, optimizer), with one of four corrections: none (ignore the mismatch), tis (truncated importance sampling, weight min(πfsdp/πvllm, C)), ppo_is (πvllm in the PPO ratio), vanilla_is (untruncated weight).

Rollouts can run in bf16, FP8 (vLLM online quantization; weight-only Marlin kernels on A100) or INT8 W8A8 (Cutlass INT8 GEMMs, per-channel weights, per-token activations). The profiler uses NVIDIA's cupti-python Activity API: kernels, memcpys, memsets and CUDA runtime/driver calls are recorded and each is assigned to the phase that launched it via CUPTI external correlation ids, with a time-window fallback for work launched from other threads (the autograd backward thread). Phases are bracketed by device synchronizations, so the wall time and the GPU-busy time of a phase can be compared directly. Training continues until the evaluation accuracy stops improving (no gain for several evaluations in a row) or a step limit is reached.

Problems found and fixed while building it

  • vLLM's extensible KV cache starved the trainer. vLLM 0.34 turns on an "extensible" KV cache that lives outside PyTorch's allocator and calls torch.cuda.set_per_process_memory_fraction to cap what PyTorch may reserve in the whole process. With the trainer in the same process, the 1.5B runs hit out-of-memory errors at a 54.5 GiB cap on an 80 GB GPU. The rollout engine now starts with enable_extensible_kv_cache=False, so the KV cache is an ordinary allocation sized by vllm_gpu_memory_utilization and the rest of the GPU stays free for training.
  • vLLM tried to JIT-compile a sampling kernel with the wrong CUDA compiler. vLLM's FlashInfer sampler compiles CUDA code on first use with whatever nvcc is on PATH; on the build machine that was CUDA 11.8, which rejects FlashInfer's flags (--compress-mode=size), so the run crashed. The FlashInfer sampler is now off (VLLM_USE_FLASHINFER_SAMPLER=0) and vLLM uses its PyTorch sampler, which needs no compiler and keeps sampling numerics independent of the local toolkit. All JIT and compile caches (vLLM, Triton, Inductor, FlashInfer) now go under RLPROF_HOME.
  • Gradient checkpointing was silently off. transformers' from_pretrained returns the model in eval mode, and its gradient checkpointing only runs in train mode, so every layer's activations were kept and the 1.5B runs ran out of memory in the forward pass. The trainer now calls model.train(); the Qwen models used have no dropout, so nothing else changes.
  • The lockfile mixed two CUPTI versions. cupti-python 13.5 requires CUPTI 13.5, while torch 2.14 pins CUPTI 13.0.85, so a clean install from the lockfile could not be resolved. The lockfile now pins cupti-python 13.0.1 with nvidia-cuda-cupti 13.0.85; a fresh environment built from it ran the full pipeline. The profiler also no longer depends on cupti.get_version(), which only exists in cupti-python 13.2 and later.
  • Smaller ones: the trainer's entropy pass now uses two vocabulary-sized buffers per chunk instead of four (head_chunk_tokens, default 2048); a run that reuses a name starts with a clean directory instead of appending to the old metrics.jsonl; the kernel categorizer recognizes vLLM's Cutlass INT8 (enable_sm80_to_sm89 … GemmWithVisitorIa) and Marlin FP8 GEMMs by explicit rules.

Status

  • Done (2026-11-22): four Qwen2.5-0.5B-Instruct / GSM8K runs, CUPTI on every step, each stopped when eval accuracy (500 test problems, every 10 steps) did not improve for 5 evals.
    • bf16 rollouts + TIS: 210 steps, eval 0.486 → best 0.600 (step 160).
    • bf16 rollouts, no correction: 130 steps, best 0.564 (step 80).
    • int8 rollouts + TIS: 300 steps, 0.446 → best 0.606 (step 250); KL k3 grew from 0.009 to 0.028.
    • int8 rollouts, no correction: 90 steps, best 0.534 (step 40), then fell to 0.480 as KL k3 grew to 0.044. "Converged" here is the stop rule's name; this run was getting worse.
  • CUPTI overhead: 16.9 s per step without profiling, 20.9 s with it (+24%, both GPUs, both run orders). Most of it is in the rollout (6.6 s → 9.4 s), where decoding launches many small kernels; old_logprob adds 0.9 s and training about 0.3 s. The phase times on this page include that overhead.
  • Not done: one seed per setting; the other datasets and models in the registry were only run as short smoke tests; GPUs were shared with other jobs, so timings can vary.
